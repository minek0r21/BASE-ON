# BASE:ON 통합 설계 v0.1 — TRD v1.0 기준

> 작성 2026-10-16 (7주차). 근거 자료는 맨 아래 「근거」에 있다.
> 이 문서는 **TRD v1.0(2026-10-16)을 요구사항의 기준으로 두고**, BASEON 코드(FastAPI + Neo4j 프로토타입)를 그 요구에 맞추는 설계다.
> statscene·statscene-neo4j(Spring 설계·검증 기록)에서는 **데이터 정확성 규칙과 검증 수치만** 가져온다.
> 숫자 중 "재계산"이라고 적은 것은 2026-10-16에 BASEON `etl/prepare.py`를 리비전 `6afc8af` parquet(2024~2026)에 그대로 돌려 얻은 값이다.

## 4. 목표 아키텍처

```
[로컬 PC — 적재 전용]
  parquet 스냅샷 (리비전 6afc8af, SHA256SUMS)      공식 채널 영상 인벤토리 (+ 필요 시 YouTube Data API 증분)
  선수 프로필 CSV                                    │
          │                                         │
          └──────────── ETL (Python, pandas) ───────┘
                        00 초기화 → 01 핵심 → 02 시즌·백분위 → 05 프로필 → 06~08 영상 → 09 스냅샷 → 03 검증
                        │
                        ▼
                 Neo4j (로컬)  ──neo4j-admin dump──▶  .dump 파일
                                                         │ (업로드 후 load)
[서버 1대 — Docker Compose]                               ▼
  Caddy :443 (HTTPS)
   ├─ /            → Next.js 정적 파일 (out/)
   ├─ /api/v1/*    → FastAPI (uvicorn 2 workers)  ── bolt(내부망) ──▶ Neo4j (7687·7474 외부 비공개)
   └─ /api/v1/admin/* → FastAPI (관리자 토큰 필수, 호출 이력 기록)
  backup (cron)  → 매일 사람 데이터(MATCHED_TO 검수 결과·감사 로그) JSON 내보내기 → 서버 밖 사본
  FastAPI → YouTube Data API (videos.list, 신고 판정 때만. 키는 서버 환경변수)

[브라우저]  Next.js 화면 ──▶ YouTube IFrame Player (videoId + start/end, 다운로드·재호스팅 없음)
```

| 구성 | 결정 | 이유 |
| --- | --- | --- |
| 프론트 서빙 | Next.js `output: 'export'` → Caddy가 정적 파일로 서빙 | 서버 렌더링이 필요한 기능이 없다. Node 프로세스가 없어 메모리 약 150~250MB 절약 |
| 선수 상세 주소 | `/players/[id]` — 빌드 때 `generateStaticParams`로 847명 페이지를 만든다 | 선수 목록이 스냅샷 고정이라 빌드 시점에 확정된다 |
| 캐시 | 없음. 필요하면 FastAPI 프로세스 안(`cachetools` TTL) | 리그 전체 쿼리(`/batters`, `/leaders`, `/standings`)만 후보. NFR-01은 선수 상세 기준 |
| ETL 위치 | 로컬에서 적재 → dump/load | 2GB 서버에서 pandas 가공은 메모리 위험. `00`은 대화형 |
| Neo4j 이미지 | `neo4j:2026.09.0-community` 패치까지 고정, 힙 512MB·페이지 캐시 256MB | statscene V-08 실측: 적재 후 컨테이너 1.28GB |
| 서버 크기 | 4GB 권장 (t3.medium 또는 학교 클라우드 동급). 2GB면 스왑 2GB 필수 | Neo4j 1.28GB + FastAPI 약 150MB + Caddy + OS → 2GB는 한계선 |

| `review_reason` | `low_score` · `ambiguous` · `chapter` · `unplayable` · `unparsed` | 검수 큐 구분 (신규 후보 / 영상 소실) |

| `reviewer`, `reviewed_at`, `moved_to` | | 지금과 같음. `reviewer`는 본문이 아니라 **토큰에서** 정한다 |

**화면에 보이는 연결(= 확정):** `status IN ['auto_confirmed','approved'] AND v.playable`. 한 홈런에 여러 개면 `scene` > `inning` > `game` 순서로 하나.
**사람 데이터:** `approved`·`rejected`·`origin = 'manual'`·`ReviewLog`는 parquet에서 다시 만들 수 없다 → ETL이 지우거나 덮어쓰지 않고, 매일 백업한다 (10-3).

### 6-4. 관리자 인증 (SEC-01·07)

- 방식: 환경변수 `ADMIN_TOKENS="이름1:토큰1,이름2:토큰2"`(팀원 4명). 요청 헤더 `Authorization: Bearer <토큰>`. FastAPI `Depends(require_admin)`가 토큰으로 검수자 이름을 정한다 — **본문의 `reviewer` 칸은 없앤다.**
- 비교는 `secrets.compare_digest`. 토큰은 32바이트 무작위, 저장소·프론트 코드에 넣지 않는다(SEC-02와 같은 취급).
- 관리자 화면은 토큰 입력 칸 하나. `sessionStorage`에만 두고 탭을 닫으면 사라진다. 공개 화면에 링크 없음(StoryBoard BO-AD-01).
- 모든 `/admin` 쓰기 요청은 `ReviewLog` 노드 하나를 같은 트랜잭션에서 만든다. 읽기 요청은 uvicorn 접근 로그로 충분하다.
- 신고 API(API-12)는 인증 없음. 대신 같은 IP 분당 10회 제한(프로세스 안 카운터)과 videoId 24시간 판정 캐시.

### 7-2. 재실행 안전성 (HANDOFF 「높음」 해결)

```cypher
// 08 시작 전: 이번 시즌 범위의 자동 생성물만 지운다
MATCH (pa:PlateAppearance {season: $season})-[c:CANDIDATE]->() DELETE c;
MATCH (pa:PlateAppearance {season: $season})-[m:MATCHED_TO]->()
WHERE m.origin STARTS WITH 'auto' AND m.status IN ['pending', 'auto_confirmed']
DELETE m;
```

- 이후 `MERGE`는 지금과 같다. 사람이 승인·반려한 연결은 위 조건에 걸리지 않는다.
- 07이 사람이 이미 처리한 타석-영상 쌍을 다시 내면 `MERGE`가 그 연결과 만난다. 이때 `ON MATCH`에서는 아무것도 바꾸지 않는다(지금처럼 `pending`일 때만 점수를 갱신하는 분기도 위 삭제로 필요 없어진다).

### 7-3. 스냅샷 고정 (NFR-04)

- parquet은 `statscene-neo4j/data/raw/kbo_pbp/`의 시즌별 파일 4개(2023 포함, 읽을 때 제외)와 `REVISION`·`SHA256SUMS`를 그대로 쓴다. BASEON README의 「`kbo_pbp.parquet` 한 파일」 서술은 고친다.
- 01은 시작할 때 SHA-256을 확인하고, 다르면 적재하지 않는다.
- 팀 공유: parquet은 저장소에 넣지 않고 `scripts/get_data.ps1`가 Hugging Face에서 리비전 고정으로 받는다. 적재된 DB는 한 사람이 만든 dump를 공유한다.

### 7-5. 영상 매칭 — NFR-06(2026 70%)·NFR-07(오매칭 1%)

**입력:** `yt_inventory.json` 34,000개(KBO·10개 구단·TVING, 설명란 포함). 2026-07-26까지의 경기만 대상이라 2026-09-24 조회분이면 충분하다. 쿼터는 증분·신고 판정에만 쓴다.

**분류:** 경기 하이라이트(`H/L` 재생목록·「야구 하이라이트 … KBO X TVING」) / 장면 클립 / 챕터 영상(설명란 타임스탬프 3줄 이상) / 기타.

**제목 형식:** 지금 `RE_TEAMS`는 `[A vs B] 내용 | M.D |`만 읽는다. `내용 | A vs B | M.D |` 형식과 구단명 풀네임(「롯데자이언츠」), 구단 채널(채널 = 팀)을 추가한다. 날짜가 없으면 게시일(KST)과 그 전날을 후보로 둔다 (`statscene-neo4j/tools/verify/match_hr.py`의 `video_dates`·`teams_in`을 옮긴다).

**점수(07, 유지):** 후보 정렬과 검수 화면의 「왜 검수에 왔나」에 쓴다.

**자동 확정 조건 (`auto_confirmed`) — 모두 만족해야 한다. 하나라도 어긋나면 `pending`:**
1. 장면 클립 경로 (챕터는 자동 확정하지 않는다)
2. 제목에 날짜가 있다 (게시일 추정 날짜는 안 됨)
3. 성명이 그 경기 `batter_name`과 완전히 일치 (경기 당시 이름이라 개명 문제 없음)
4. 그날 그 타자의 홈런이 1개. 2개 이상이면 제목에 백투백·멀티·연타석이 있을 때만 전부 연결
5. 제목의 n호·타점(솔로~만루)이 있으면 계산값과 일치
6. 인터뷰·덕아웃캠·비하인드·모음 제목이 아니다
7. 점수 ≥ 70 이고 1·2등 차 ≥ 20

**예상치 (statscene V-04 실측, 같은 인벤토리):** 2026 `scene` 천장 68~75%, 클립 자동 확정 약 554건(64%). **604건까지 약 50건이 모자라 검수(느슨한 클립 약 48 + 챕터 약 46)와 수동 표시로 채운다.** 여유가 작으므로 2026 검수를 9주차 안에 시작한다.

**오매칭 기계 검사 (자동 확정 전에 거른다):** 제목 득점 수 ↔ `runs_scored`, n호 ↔ `hr_seq`, 이닝 ↔ `inning`, 끝내기 ↔ `situation`, 동명이인 홈런 타자(김민혁·이재원) → 걸리면 `pending`(`review_reason = ambiguous`).

## 8. 영상 재생·신고·검수

### 8-1. 재생 버튼 표시 (FR-03-02·03)

- ▶(노랑) = 확정 `scene`, 테두리 버튼 = 확정 `inning`, 「경기 하이라이트」 = `game`, 그 밖은 「연결된 영상 없음」 (StoryBoard 장면 칩 3종).
- `pending`·`rejected`·`playable = false`는 버튼을 그리지 않는다.

### 8-2. 플레이어 컴포넌트 (FR-04-01·02)

- 썸네일(`https://img.youtube.com/vi/{id}/mqdefault.jpg` 핫링크)을 먼저 그리고, 누를 때 iframe을 넣는다. 자동재생 없음.
- `player.loadVideoById({videoId, startSeconds, endSeconds})` (statscene V-03b: 시작·종료 오차 0.1초 안).
- **종료 강제 (TRD FR-04-02):** 재생 중 250ms마다 `getCurrentTime()`을 보고 `> end_sec`이면 `pauseVideo()` 후 `seekTo(end_sec)`. 사용자가 진행바로 종료 뒤로 옮겨도 멈춘다. 시작 앞 되감기는 막지 않되, 버퍼링 정체를 감지하면 `seekTo(start_sec)`로 다시 건다(V-03b에서 확인된 정체).
- 같은 경기 다른 타석으로 바꿀 때 iframe을 다시 만들지 않고 `loadVideoById`만 부른다 (TS-05 「같은 경기 내 타석 전환 재생」).
- `onError` 100·101·150·153 → 「영상을 재생할 수 없습니다」 표시 + API-12 신고.
- **배포 도메인에서 임베드 재확인 필수** — `file://`·일부 내장 브라우저에서 오류 153·5가 났다(statscene 10-13 기록).

### 8-3. 재생 불가 처리 (FR-04-03, T9)

1. 클라이언트: `POST /video-links/{video_id}/report` — 항상 202, 상태를 바꾸지 않는다.
2. 서버: 같은 `video_id`를 24시간 안에 확인했으면 끝. 아니면 `videos.list?part=status&id=…` (쿼터 1).
3. `items`가 비었거나 `embeddable = false` → `VideoLink.playable = false`, 그 영상의 확정 연결 전부 `status = 'pending'`, `review_reason = 'unplayable'` → 검수 「영상 소실」 큐. `ReviewLog`에 `reviewer = 'system'`으로 남긴다.
4. 정상 응답이면 아무것도 바꾸지 않는다(사용자 쪽 일시 오류).
- 주기 재확인: 확정 영상 `video_id`를 주 1회 50개씩 같은 판정 함수로 확인 (backup 컨테이너의 cron에서 내부 엔드포인트 호출).

### 8-4. 검수 화면 (FR-08, BO-AD-01)

| 큐 | 들어오는 것 | 처리 |
| --- | --- | --- |
| 신규 후보 | `pending` (`low_score`·`ambiguous`·`chapter`·`unparsed`) | 승인 · 시작/종료 고쳐 승인(`retime`) · 반려 · 다른 타석으로 옮김 |

### 10-2. 서버

- **학교 클라우드는 사용 희망일 2주 전 신청** (TRD). 13주차(11/23 주) 전시에 쓰려면 **늦어도 11/9까지, 리허설(12주차)까지 고려하면 지금 신청**.

- API는 Neo4j healthcheck 통과 후 시작(`depends_on: condition: service_healthy`).
- CORS 허용 주소는 환경변수 `CORS_ORIGINS`. 같은 도메인에서 Caddy가 함께 서빙하면 CORS가 필요 없다.
